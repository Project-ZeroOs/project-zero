## 1. IDENTITY FORENSICS

### 1.1 Identity Disambiguation Matrix
We independently audit the 14 fundamental identity types defined across the ZeroOS architecture layers. Each identity represents a distinct entity in the system domain:

```text
WorkspaceId      : [uint128 UUIDv4]      - Isolated workspace boundary container
ObjectId         : [uint128 UUIDv4]      - Universal filesystem / workspace object identity
WorkloadId       : [uint128 SHA256-128]  - Deterministic semantic execution specification
AgentId          : [uint128 UUIDv4]      - Autonomous reasoning context / identity handle
ProcessId        : [uint64  pid_t]       - Transient kernel task table descriptor
CapabilityHandle : [uint64  cap_handle_t]- Kernel object access capability index
ResourceId       : [uint128 UUIDv4]      - Hardware/fabric physical/virtual resource handle
IntentNodeId     : [uint128 UUIDv4]      - Node within high-level intent DAG
IntentId         : [uint128 UUIDv4]      - User high-level goal submission
PlanId           : [uint128 UUIDv4]      - Versioned intent realization plan
PlanStepId       : [uint128 UUIDv4]      - Individual step within a Plan graph
ExecutionId      : [uint128 UUIDv4]      - Single concrete runtime execution attempt span
ObservationId    : [uint128 SHA256-128]  - Immutable semantic event observation unit
ExecutionEventId : [uint128 UUIDv4]      - Single authoritative execution journal entry ID
```

### 1.2 Mathematical Proofs of Non-Equivalence

#### Proof 1: WorkloadId ≠ ExecutionId
- **WorkloadId** is a deterministic content-addressed hash of the immutable workload specification (`hash(PlanId, PlanStepId, Inputs, Spec)`). Multiple execution attempts (retries, recoveries) for the same workload share the exact same `WorkloadId`.
- **ExecutionId** is a globally unique random UUIDv4 assigned to a single, specific execution span attempt.
- $\therefore \text{WorkloadId} \neq \text{ExecutionId}$.

#### Proof 2: ExecutionId ≠ ProcessId
- **ExecutionId** is a persistent, workspace-managed lifecycle tracking handle (UUIDv4) spanning pre-admission, resource allocation, process spawning, process crash recovery, and post-execution cleanup.
- **ProcessId** is a transient 64-bit kernel task descriptor (`pid_t`) created by `sys_spawn` and destroyed when the OS process exits. An `ExecutionId` can map to zero processes (admitted), one process (running), or sequentially multiple processes (crashed & restarted process within recoverable execution span).
- $\therefore \text{ExecutionId} \neq \text{ProcessId}$.

#### Proof 3: ObservationId ≠ ExecutionEventId
- **ExecutionEventId** is a low-level, authoritative, append-only journal record ID generated by `workspaced` recording physical system lifecycle mutations (`EXECUTION_STARTED`, `PROCESS_BOUND`, `PROCESS_EXITED`).
- **ObservationId** is a workspace-visible, content-addressed semantic interpretation derived from execution output, exit codes, artifacts, or state assertions.
- $\therefore \text{ObservationId} \neq \text{ExecutionEventId}$.

#### Proof 4: ExecutionId ≠ PlanId & ExecutionId ≠ PlanStepId
- **PlanId** and **PlanStepId** belong to the intent planning abstraction layer. A step in a plan specifies *what* needs to be done.
- **ExecutionId** belongs to the concrete runtime execution layer. It tracks a specific execution *attempt* of the workload materialized from a plan step.
- $\therefore \text{ExecutionId} \neq \text{PlanId} \land \text{ExecutionId} \neq \text{PlanStepId}$.

### 1.3 Audit for Identity Representation Anti-Patterns
We checked for illegal aliasing or improper primitive representation of identities:
- **Array Indexing**: 🟢 NO identities are represented as array offsets or table indices. All handles use strong scalar types (`uint128` or `uint64`).
- **Process IDs**: 🟢 No persistent IDs borrow kernel PIDs. PID is strictly scoped to `ProcessId`.
- **Filesystem Paths**: 🟢 Paths are object attributes; no path is used as a surrogate key for Workload, Execution, or Observation.
- **Strings**: 🟢 Hex/UUID strings are restricted to serialization; in-memory and disk structures use binary fixed-width 64/128-bit fields.
- **Pointers**: 🟢 Zero in-memory raw pointers used as cross-boundary identifiers.
- **Timestamps / Sequence Numbers**: 🟢 Timestamps and sequence numbers are strictly attributes of `ExecutionEvent`, never entity identifiers.

### 2.2 Formal State Property Verification
- **Terminal States**: `COMPLETED`, `FAILED`, `TIMED_OUT`, `INVALIDATED`, `CANCELLED`.
- **Resurrection Prevention**: Once in any terminal state, outgoing transitions are strictly 0. Any attempt to write a transition out of a terminal state is rejected by `workspaced` state guard assertions.
- **Recovery Semantics**: `INTERRUPTED` is the single non-terminal fault state allowed to transition back to `RUNNING` under process restart policy without changing `ExecutionId`. If recovery fails, it transitions deterministically to `FAILED`.

## 3. WORKLOAD vs EXECUTION vs PROCESS

### 3.1 Boundaries & Definitions
- **Workload**: Immutable, persistent, content-addressed specification (`WorkloadId`).
- **Execution**: Durable, stateful runtime attempt span (`ExecutionId`).
- **Process**: Transient kernel task (`ProcessId`).

### 3.2 Scenario Test Evaluation

#### Case A: Process Crashes
- **Workload Behavior**: Workload survives unharmed in persistent storage.
- **Execution Behavior**: Execution transitions to `INTERRUPTED` (if recoverable) or `FAILED` (if non-recoverable).
- **Process ID Assignment**: If recovered, the newly spawned kernel process receives a **new ProcessId** (`pid_t` assigned by kernel), while the active execution retains the **same ExecutionId**.

#### Case B: Execution Fails
- **Workload Retry**: The Workload specification survives. A new retry attempt may be scheduled.
- **Execution ID Assignment**: The failed ExecutionId enters terminal state `FAILED`. The retry attempt receives a **brand-new ExecutionId** ($\text{ExecutionId}_2 \neq \text{ExecutionId}_1$).

#### Case C: Process Restarts under Recovery
- **State Integrity**: `workspaced` validates execution lease and recovery count. The process is re-bound (`PROCESS_BOUND` event appended with new `ProcessId`), execution state returns to `RUNNING`. Identity is preserved without corruption.

#### Case D: Concurrent Execution Invariant Audit
- **Invariant**: $\text{ActiveExecutions}(\text{WorkloadId}) \le 1$.
- **Verification**: `workspaced` maintains an in-memory active execution index backed by a transactional filesystem lock table (`.lock` record per `WorkloadId`). Admitting a second execution for an active `WorkloadId` fails with `ERR_WORKLOAD_ALREADY_ACTIVE`.
- **Verdict**: Enforced as an **architectural invariant** at `workspaced` daemon boundary.

## 5. EVENT LOG vs OBSERVATION

### 5.1 Architectural Separation

```text
[ Kernel Process Exit / System Event ]
                 │
                 ▼
     ┌───────────────────────┐
     │    ExecutionEvent     │  <-- Authoritative Execution History (System-Internal, Immutable Log)
     └───────────────────────┘
                 │
                 ▼
     ┌───────────────────────┐
     │      Observation      │  <-- Semantic Workspace-Visible Evidence (Read-Only for Planner/Agent)
     └───────────────────────┘
```

### 5.2 Property & Protection Checks
1. **Observation Mutation of Authoritative State**: 🟢 IMPOSSIBLE. Observations are pure downstream projections of state. An Observation contains zero capability to mutate kernel, workload, or execution states.
2. **Agent Rewriting History**: 🟢 IMPOSSIBLE. Execution events and observations are appended to read-only workspace storage (`.zero/workspace/journal/`). Agents possess read-only capabilities for observations.
3. **Observation Provenance Requirement**: 🟢 ENFORCED. Every `Observation` structure must include explicit cryptographic provenance bindings:
   ```text
   Observation {
       ObservationId : SHA256(ExecutionId, EventSeq, PayloadHash),
       ExecutionId   : UUIDv4,
       WorkloadId    : SHA256-128,
       Provenance    : ExecutionEventRef { EventId, SequenceNum }
   }
   ```
   Observations lacking valid event provenance are rejected during workspace ingestion.

## 6. EVENT ORDERING

### 6.1 Order Primitive Analysis

The architecture specifies a composite ordering key:
$$\text{OrderKey} = \langle \text{SequenceNum}_{64}, \text{TimestampTSC}_{64} \rangle$$

1. **Authoritative Primitive**: Monotonic `SequenceNum_{64}` assigned strictly by the single-threaded event append loop in `workspaced`.
2. **Role of Hardware TSC**: `TimestampTSC` is **informational only** (used for performance profiling and latency calculation).
3. **Multi-Core / SMP TSC Drift**: Because hardware TSC can drift across sockets or CPUs, `TimestampTSC` is **not used** for logical event ordering.
4. **Backward Movement & Out-of-Order Events**: `SequenceNum_{64}` is strictly incremented ($N+1$) per workspace journal record. Monotonic sequence numbering prevents reordering or backward timestamp jumps.
5. **Surviving Restarts**: `workspaced` reads the highest `SequenceNum` from the header of the persisted 2PC journal log upon startup. The next event gets $\text{SequenceNum}_{\text{last}} + 1$. Sequence numbers never reset during workspace lifetime.
6. **Forger Protection**: `SequenceNum` generation is protected by kernel IPC capability checks; external agents cannot inject or force sequence numbers.

## 7. EVENT IDEMPOTENCY

### 7.1 Adversarial Event Replay Attacks

#### Attack Scenario 1: Duplicate `EXECUTION_STARTED`
- **Injected Stream**: `EXECUTION_STARTED`, `EXECUTION_STARTED`, `EXECUTION_STARTED`
- **Handling**: The first `EXECUTION_STARTED` advances state from `ADMITTED` → `RUNNING`. Subsequent duplicate events fail state-machine validation (`CurrentState == RUNNING` does not accept `EXECUTION_STARTED`). The duplicates are logged as idempotency-no-ops or rejected as invalid state transitions.

#### Attack Scenario 2: Duplicate `EXECUTION_COMPLETED`
- **Injected Stream**: `EXECUTION_COMPLETED`, `EXECUTION_COMPLETED`
- **Handling**: First event transitions state `RUNNING` → `COMPLETED` (terminal). Second event encounters terminal state `COMPLETED` and is immediately dropped.

#### Attack Scenario 3: Conflicting Terminal Events
- **Injected Stream**: `EXECUTION_FAILED`, `EXECUTION_COMPLETED`
- **Handling**: `EXECUTION_FAILED` sets terminal state `FAILED`. Subsequent `EXECUTION_COMPLETED` attempt is rejected because `FAILED` is a terminal state.

#### Attack Scenario 4: Out-of-Order Arrival (`COMPLETED` before `STARTED`)
- **Injected Stream**: `EXECUTION_COMPLETED` (Seq 2), `EXECUTION_STARTED` (Seq 1)
- **Handling**: `workspaced` processes events in strict `SequenceNum` order. If out-of-order sequence arrival occurs across IPC buffers, events are sorted by `SequenceNum` before evaluation. If sequence gap exists, processing halts until missing sequence numbers arrive or timeout triggers recovery.

## 8. CRASH CONSISTENCY

### 8.1 Crash Point Analysis & Replay Recovery

We evaluate system crash & power-loss resilience across 6 specific crash points:

```text
(1) Before Append ──> (2) During Append ──> (3) After Append/Pre-State ──> (4) Pre-Observation ──> (5) Pre-Persistence ──> (6) Pre-ACK
```

1. **Crash Point 1: Before Event Append**
   - *State*: Event not recorded. Execution remains in previous verified state.
   - *Recovery*: Replay of uncommitted operation cleanly re-attempts event creation. No phantom entries.
2. **Crash Point 2: During Event Append**
   - *State*: Partial event written to disk journal.
   - *Recovery*: On startup, journal CRC check detects corrupt tail record. Journal truncates partial record to last valid entry. Operation re-executes cleanly.
3. **Crash Point 3: After Event Append, Before State Derivation**
   - *State*: Journal contains durable event record, but in-memory execution state vector is unupdated.
   - *Recovery*: `workspaced` replays journal from last checkpoint, deriving identical state vector.
4. **Crash Point 4: After State Derivation, Before Observation Ingestion**
   - *State*: State is updated, but observation record hasn't been emitted.
   - *Recovery*: In-memory engine checks latest state against observation log; missing observation is deterministically re-synthesized from the durable event log entry.
5. **Crash Point 5: After Observation, Before Disk Persistence**
   - *State*: State updated in RAM, observation in RAM, disk pending flush.
   - *Recovery*: Disk flush fails; system restarts, journal recovery re-derives state and re-flushes observation.
6. **Crash Point 6: After Persistence, Before IPC ACK**
   - *State*: Event, state, and observation fully durable on disk; caller crashed before receiving ACK.
   - *Recovery*: Caller re-queries state on reboot; system returns already-persisted success status. Idempotent.

## 10. RESOURCE BOUNDARY

### 10.1 Boundary Compliance Audit
- **Arbitrary Allocation**: 🟢 Execution subsystem cannot allocate arbitrary resources. Resource demands must pass through `resourced` and `schedulerd`.
- **Physical Hardware Selection**: 🟢 Execution subsystem does not interact directly with hardware devices; it only receives resource allocation leases from `schedulerd`.
- **Identity Minting**: 🟢 Execution subsystem cannot mint `ResourceId` or resource leases. All leases are cryptographically signed by `resourced`.
- **Quota & Isolation Bypass**: 🟢 Workspace resource quotas enforced by `resourced` cannot be overridden by `workspaced` or execution instances.

## 11. CAPABILITY BOUNDARY

### 11.1 Capability Escalation Vectors Audit

- **Escalation via Observation**: 🟢 Observations are unprivileged data payload structures. They convey zero kernel capability handles.
- **Escalation via Replanning**: 🟢 Planner cannot grant new capabilities. New plans are evaluated against the existing workspace capability envelope during workload materialization.
- **Stale Capabilities after Workspace Deletion**: 🟢 Deleting a workspace invalidates the workspace capability master key at kernel level. All derivative handles return `ERR_CAPABILITY_INVALID`.
- **Capability Use Post-Migration**: 🟢 Executions migrating across fabric nodes must undergo capability re-authoring via `workspaced` and kernel IPC; old node capabilities are explicitly revoked.
- **Cross-Workspace Leakage**: 🟢 Capability handles are scoped to a specific kernel process table and workspace context. Passing a handle number across workspace boundaries fails capability lookup in kernel.

## 12. WORKSPACE BOUNDARY

### 12.1 Isolation Security Tests
- **Workspace A → Observation → Workspace B Leakage**: 🟢 Ingestion of observations from another workspace is prohibited unless an explicit cross-workspace sharing capability handle is presented to `workspaced`.
- **Workspace Lifecycle Operations**:
  - *Suspension*: Suspends all active executions within the workspace; freezes event logging.
  - *Archive*: Serializes workspace journal and object state to read-only image; releases all active resource leases.
  - *Deletion*: Revokes all workspace capability handles, cleans up persistent directories, and terminates active processes.
  - *Resume*: Re-validates resource quotas, restores execution state indices, and resumes non-terminal workloads.

## 14. REPLANNING FORENSICS

### 14.1 Immutability of Completed Workload Execution History
- When an observation triggers replanning:
  - `Plan v1` remains immutable in workspace record.
  - Completed `WorkloadId` items executed under `Plan v1` are **never deleted or re-executed**.
  - `Plan v2` references completed outputs from `Plan v1` as fixed input bindings.
  - Historical observations and execution events for `Plan v1` remain locked.

### 14.2 Plan Version Racing Scenarios
- **Scenario A**: `Plan v1` is running while `Plan v2` is created.
  - *Handling*: `workspaced` marks `Plan v1` as `SUPERSEDED`. Active executions under `Plan v1` are either allowed to gracefully complete (if non-conflicting) or issued `EXECUTION_CANCELLED` prior to `Plan v2` workload materialization.
- **Scenario B**: `Plan v1` and `Plan v2` attempt to execute the exact same semantic step.
  - *Handling*: Workloads derived from identical steps share identical `WorkloadId`s. Because $\text{ActiveExecutions}(\text{WorkloadId}) \le 1$, duplicate execution attempt by `Plan v2` is blocked if `Plan v1` execution is already active, or skipped if `Plan v1` execution already reached `COMPLETED`.

## 15. CONCURRENT REPLANNING

### 15.1 Concurrent Plan Creation Audit
- **Scenario**: `Observation A` triggers `Plan v2` request while concurrent `Observation B` triggers `Plan v3` request.
- **Serialization Authority**: `workspaced` single-threaded plan transition engine.
- **Resolution**:
  1. `workspaced` acquires plan mutation lock (`plan.lock`).
  2. First request is assigned version index `v2` and validated against current workspace state snapshot.
  3. Second request attempting to write `v3` based on stale baseline state is rejected with `ERR_PLAN_VERSION_STALE`.
  4. The second agent/planner must fetch updated `v2` state and re-submit. Duplicate materialization is strictly prevented.

## 16. OBSERVATION SEMANTICS

### 16.1 Categorization of Fact Levels

Every observation must explicitly state its factual depth:

1. **Raw Fact (`OBS_FACT_RAW`)**: Direct verifiable low-level output (e.g., Process exit code = 0, File `output.dat` written, 4096 bytes).
2. **Derived Fact (`OBS_FACT_DERIVED`)**: Calculated property from raw facts (e.g., Hash of `output.dat` matches expected digest).
3. **Interpretation (`OBS_INTERPRETATION`)**: Higher-level classification (e.g., Test suite passed with 100% coverage).
4. **Inference (`OBS_INFERENCE`)**: Agent-driven hypothesis (e.g., Code performance optimized by 15% based on benchmark timing).

*Validation Requirement*: Models must not treat an `Inference` or `Interpretation` as an immutable `Raw Fact`. Confidence metrics (0.00 – 1.00) apply strictly to `Inference` types.

## 17. OBSERVATION TRUST

### 17.1 Provenance and Authenticity Enforcement
- **Malicious Workload Attack**: A workload attempts to write a fake observation file into the workspace directory.
  - *Defense*: Workspace directory watchdogs reject any observation file not bearing a valid cryptographic HMAC signature generated by `workspaced`.
- **Malicious Agent Attack**: Agent submits a forged observation to bypass an approval gate.
  - *Defense*: `workspaced` checks `ObservationId` against internal `ExecutionEvent` cross-reference index. Unmatched observations are discarded as unauthenticated.

### 19.2 Audit Across Failure & Concurrency Edge Cases
- **Concurrent Schedulers**: Atomic file lock on `workspaced` workload lockfile prevents multi-scheduler double-admission.

- **Node Recovery**: Node partition recovery double-checks lease validity with `resourced`. Stale node executions are killed before new execution is spawned.
